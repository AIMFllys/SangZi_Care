# GitHub Issues #1–#6 依赖有序修复设计

> 创建日期：2026-08-13
> 状态：已接受（用户授权无人值守推进）
> 适用仓库：`AIMFllys/SangZi_Care`
> 目标：完整修复当前全部 GitHub Issues，并以真实 Android Debug APK 端测和统一工程门禁验证

## 1. 背景与现状结论

仓库当前共有 6 个开放 Issue。Issue 文本来自 2026-07-15 的快速代码扫描，不能直接当成当前实现真相；本轮先对 live Issue、当前代码、测试、迁移和 Android 壳进行交叉审计，再确定修复范围。

审计结论：

- #1 的 ASR、语音消息发送和普通文字发送都已存在，但转写结果仍停留在语音预览，不能进入可编辑文字草稿。
- #2 尚无联系人备注、置顶、持久化偏好或聊天标题投影。
- #3 只记录 `oc_emergency_calls`，没有向亲友消息表写入 SOS 消息；前端却无条件显示“已通知家属”。
- #4 活动中的 `/voice` 页面没有为长回复设置独立滚动区。
- #5 数值字段因为一个扁平 state 而“偶然”跨 Tab 保留，但备注、录入方式和语音状态会串 Tab；提交只保存当前 Tab，也没有离开确认。
- #6 的 MiMo 工具注册、健康写入、低语保存和同意后分享主体已经存在；真实缺口是客户端丢弃 `actions`、失败/无收件人不可见，以及缺少跨层与端侧闭环证据。

## 2. 依赖顺序

执行顺序固定为：

```text
#1 转写进入可编辑消息草稿
  ↓ 建立客户端“动作结果进入可见状态”的模式
#6 AI 工具调用与亲友消息闭环
  ↓ 固化服务端动作结果、消息分类和亲友扇出原则
#3 SOS 原子消息通知
  ↓ 消息生产端稳定后再调整联系人读取投影
#2 联系人备注与置顶
  ↓ 联系人页完成后不再影响语音页
#4 AI 长回复卡片滚动
  ↓ 独立 UI 风险收敛
#5 多类型健康草稿、批量保存与离开保护
```

顺序不机械按编号，理由如下：

1. #1 和 #6 都会改动用户输入/AI 动作反馈体验；先建立清晰的可编辑草稿，再让 AI 动作结果进入同一套可见反馈模型。
2. #6 已有主体实现，应在新增 SOS 消息扇出前确认已有 RPC 和消息分类边界，避免复制旧逻辑或恢复废弃的 `intentHandlers`。
3. #3 与 #6 都生产亲友消息，但收件人策略不同；先抽象共同的服务端结果和日志规则，再独立实现 SOS 权限筛选。
4. #2 只改变联系人读取和展示投影，应在三类消息生产端稳定后进行，避免把备注名误用于鉴权或收件人身份。
5. #4 与 #6 共用 `/voice` 页面；#6 的动作反馈先落位，#4 再一次性确定短屏、横屏和长文本几何。
6. #5 是独立但风险最高的事务、表单与 WebView 返回链路，放在最后可复用 #2 的无障碍 Dialog，并在最终 Android 回归前集中验证。

## 3. 不可破坏的架构边界

### 3.1 Next.js 与部署

- 继续使用 Next.js App Router 与 `app/api/**/route.ts`。
- 不新增 Python 后端，不恢复 `backend/`。
- 不在 `next.config.ts` 增加 `output: 'export'`；EdgeOne 产物继续为 `.next`。
- 浏览器只调用同源 API；服务端 secret 不进入 `NEXT_PUBLIC_*`。

### 3.2 身份与数据

- actor 必须由服务端校验的 Supabase JWT 决定，客户端传入的 user id 不能作为授权依据。
- 普通聊天、AI 低语、SOS 的收件人规则分别为：

| 来源 | 消息分类 | 收件人 | 额外授权 |
|---|---|---|---|
| #1 普通文字 | `chat` | 当前有效绑定中的单一 peer | 当前用户是绑定参与者 |
| #6 AI 低语 | `murmur` | 所有 active 家属 | 长辈明确同意，RPC 再校验 |
| #3 SOS | `system` | active 且 `can_receive_emergency` 的家属 | actor 必须是 elder |

- 联系人备注/置顶是 owner 私有偏好，不得修改用户全局姓名，也不得复用家庭关系字段。
- 多条健康记录必须在数据库单事务内全成全败；客户端循环调用单条接口不算事务。

### 3.3 Android 在线壳

- Android 仍是在线 WebView 壳，Release 打开正式 HTTPS 域名，Debug 才打开 `http://127.0.0.1:7742`。
- 不注入业务 JSBridge。硬件返回保护使用可取消的 DOM 事件；页面未取消时才执行 WebView 历史返回。
- 本轮本机没有物理设备，因此每个 Loop 使用实际构建、安装并启动的 Debug APK 在 API 35 AVD 上验证。模拟器、mock API、真实线上账号三种证据必须分开标注。
- Release APK 只有在部署 revision 等于源码 HEAD、签名配置存在并且正式域名可验证时才可声明完成；Debug/AVD 不能冒充 Release/物理机证据。

## 4. 共享实现原则

### 4.1 结构化动作结果

服务端可产生副作用的 AI/SOS 请求必须返回客户端可判定的结构化结果，而不是依赖自然语言回复猜测：

```ts
type ActionResult = {
  type: string;
  status: 'succeeded' | 'skipped' | 'failed';
  message: string;
  recipientCount?: number;
  requestId?: string;
};
```

客户端只展示脱敏、适老化文案；服务端日志记录 request id、动作类型、状态和耗时，不记录聊天原文、健康值、密钥或 Authorization。

### 4.2 对话框与操作菜单

- #2 联系人操作和 #5 离开确认复用同一无障碍 Dialog 基元。
- Dialog 具备 `role="dialog"`、标题关联、初始焦点、Esc/遮罩关闭策略、焦点回收和至少 48px 触控区。
- 长按只是 #2 的快捷方式，必须同时提供可见的“更多”按钮和键盘入口；滚动手势不得误触长按。

### 4.3 错误状态

- 空输入、空转写、无收件人、权限不足、数据库失败、网络失败都必须产生真实且可恢复的 UI 状态。
- 任何未完成的后端写入都不得显示“已通知”“已保存”一类成功文案。
- 可重试操作在 pending 时禁用重复提交；需要幂等的服务端副作用由 request key 或数据库唯一约束兜底。

## 5. 各 Issue 设计

### 5.1 Loop #1：语音转写回填可编辑文字草稿

目标行为：

1. ASR 成功且文本非空时，把规范化转写回填到 `ChatDetail` 的文字草稿并切换到文字模式。
2. 用户可继续编辑，点击发送后只走现有 `/api/v1/messages/send` 普通文字路径。
3. 保留“以语音发送”的现有能力；两条发送路径必须显式分开，避免一次操作重复发语音和文字。
4. 空转写和失败只显示提示，不覆盖用户已有手输草稿。
5. 若草稿已非空，不静默覆盖；由 UI 明确选择替换或追加，首版采用“保留原草稿并提示确认追加”。

测试重点：真实渲染 `ChatDetail + VoiceRecorder`，只替换媒体与网络边界；覆盖成功、编辑后发送、已有草稿、空文本、ASR 失败和原语音发送回归。

### 5.2 Loop #6：AI 工具调用与亲友消息闭环

目标行为：

1. 保留现有 `COMPANION_TOOLS → executeCompanionToolCall → oc_share_ai_murmur` 架构，不恢复旧意图处理器。
2. `useAIChat` 保存并暴露 `actions`；`/voice` 在 AI 回复旁显示成功、跳过或失败反馈。
3. 明确拒绝分享时返回 `skipped`；未绑定有效家属时不能只显示“已保存”，必须说明没有发送对象。
4. 工具异常返回脱敏失败动作，服务端写结构化日志；自然语言回复和动作状态互不伪装。
5. 为分享副作用补重试幂等，防止同一个工具调用重复写亲友消息。

测试重点：Route Handler 到真实工具执行器的跨层测试、RPC 参数契约、同意/拒绝/无绑定/失败/重试；Android 端验证动作反馈可见且语音主流程仍可操作。

### 5.3 Loop #3：SOS 原子消息通知

目标行为：

1. 服务端校验 actor 为 elder，并只解析 active 且有紧急通知权限的家属。
2. 一个数据库 RPC 原子写入 `oc_emergency_calls` 和每位合格家属的一条 `system/text` 消息；任一写入失败则整体回滚。
3. 每次客户端触发生成 request id，重复重试同一 request id 不重复创建呼救或消息。
4. 消息包含明确的紧急语义和服务端时间；只有取得真实位置时才包含位置，不编造定位。
5. 无合格联系人返回可理解的非成功结果；首页和用药页两个入口使用同一状态模型，pending 禁止重复点击，失败可重试。

测试重点：RPC SQL 契约、角色/权限、零收件人、幂等、失败回滚、两个 UI 入口反馈一致。

### 5.4 Loop #2：联系人备注与置顶

目标行为：

1. 新增 owner 私有联系人偏好表，以 owner + bind 唯一标识，保存可空备注和置顶状态。
2. Next API 验证 owner 是该 active bind 的参与者；客户端不可直接写偏好表。
3. 联系人展示名优先使用非空备注，否则使用 peer 姓名；列表和聊天标题共享同一投影规则。
4. 排序为置顶优先，其次最近消息时间，最后用稳定 id 打破平局。
5. 移动端长按打开操作菜单，同时保留可见“更多”按钮；滚动取消、短按仍进入聊天，键盘可完整操作。

测试重点：owner 隔离、刷新持久化、备注清空、稳定排序、列表/标题一致、手势冲突与键盘可达性。

### 5.5 Loop #4：AI 长回复卡片内部滚动

目标行为：

1. 回复卡使用 flex column 和受视口约束的最大高度；回复正文是唯一内部滚动区。
2. 短回复不产生多余滚动条；长回复可滚到末尾，麦克风和结束按钮始终可达。
3. 支持 360×640、844×390、系统大字体、Android WebView 惯性滚动与滚动边界控制。
4. 动作反馈区域与回复正文分离，不因 #6 新增内容把主控件推出视口。

测试重点：CSS 契约烟测和真实浏览器/WebView 几何检查，分别验证短文、长文、横屏和大字体。

### 5.6 Loop #5：多类型健康草稿、批量提交与离开保护

目标行为：

1. 用 `Record<HealthRecordType, HealthDraft>` 保存各 Tab 的值、备注、录入方式和语音状态，照护对象切换时不串数据。
2. 明确本次提交集合：所有已修改且非空的草稿。最终确认页列出记录类型与时间，不隐藏将要提交的项目。
3. 客户端先验证全部草稿；任一非法时定位到对应 Tab，且不发起部分写入。
4. 新增批量 Route Handler 和服务端 RPC，在一项数据库事务内写入最多 5 条健康记录。
5. 页面返回、取消、刷新和 Android 硬件返回遇到 dirty state 都使用共享确认框；保存成功后清除 dirty state。

测试重点：多 Tab 独立恢复、照护对象隔离、非法项零写入、事务全成全败、页面与 Android 硬件返回确认。

## 6. 每个 Loop 的固定闭环

每个 Issue 独立完成以下步骤：

1. 主智能体读取 live Issue、当前代码、相关迁移和既有测试。
2. 分析子智能体独立复核事实、根因、最小完整修复与回归风险。
3. 实现子智能体按 TDD 写一个聚焦失败测试，再集中修改真实代码，只运行触及范围的测试。
4. 主智能体审阅 diff、测试和架构边界；发现偏差交回原实现者修正。
5. 构建并安装真实 Debug APK，在 API 35 AVD 执行该 Issue 的端侧场景；记录 live/local/mock 边界。
6. 规格审查子智能体逐条核对 Issue 验收；代码审查子智能体检查安全、维护性、错误处理和测试有效性。
7. 修复所有阻塞意见并复审，通过后精确暂存该 Loop 文件、检查中文/secret/diff，再做本地提交。

Loop 内只跑聚焦测试和必要的 Android 场景；`lint + tsc + 全量 test + build` 留到六个 Loop 完成后的统一门禁，避免重复消耗时间。

## 7. Android 证据分层

| 等级 | 环境 | 能证明 | 不能证明 |
|---|---|---|---|
| A | Vitest/RTL/Route 测试 | 状态、校验、API 与 SQL 契约 | WebView 手势、布局、真实服务 |
| B | Debug APK + API 35 AVD + 本地 Next | 实际 APK 安装启动、WebView、手势、布局、返回键 | 正式域名、Release 签名、物理麦克风 |
| C | Debug APK + AVD + mock/测试账号 | 可重复异常分支和双角色 UI | 目标 Supabase/EdgeOne 已部署 |
| D | Release APK + 正式域名 + 双真实账号 + 物理机 | 完整生产闭环 | 无 |

本轮在 D 条件缺失时不得把 B/C 写成“真机生产通过”。但应完成所有可完成的 A/B/C，并把 D 的精确外部阻塞和复测命令记录在最终验收中。

## 8. 最终统一门禁

六个 Loop 全部结束后一次性执行：

1. `npm run lint`
2. `npm run tsc`
3. `npm test`
4. `npm run build`
5. Android unit/lint/Debug build
6. 安装最终 Debug APK，按 #1–#6 顺序回归关键场景
7. `git diff --check`、中文 U+FFFD 扫描、tracked secret/`.env`/keystore/APK 扫描
8. 确认 `next.config.ts` 无 `output: 'export'`，无 Python `backend/`，无未说明的工作树改动

只有实现、聚焦测试、最终工程门禁和当前可用等级的 Android 端测均通过，才可宣称本地修复完成。远端 Issue 状态、部署和 Release/物理机状态必须按事实单独报告。
