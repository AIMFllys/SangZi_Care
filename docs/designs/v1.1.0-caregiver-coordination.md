# v1.1.0 监护协同与界面升级设计

> 日期：2026-07-14
> 状态：accepted
> 范围：角色语义、家庭绑定、健康与用药协同、消息通知、MiMo 语音工具调用、移动端视觉与性能

## 1. 设计结论

v1.1.0 采用“家庭照护台账”作为家属端的统一体验方向：温和、可信、紧凑，以当前家人看板中上部卡片为视觉基准，保留双主题和现有圆润语言，但减少过大的字号、纵向内边距和无意义留白。

- **长辈（Elder）**：被照护者。保留自己的健康录入、用药计划、服药确认、语音陪伴和亲属消息。
- **家属（Family）**：监护人。没有独立的“自己的健康看板”；健康、用药和统计页面必须先明确当前选中的长辈，所有读写都携带长辈 ID。
- **关系语义**：绑定关系统一表示“长辈是当前监护人的谁”，例如父亲、母亲、爷爷、奶奶、外公、外婆、配偶、其他长辈。联系人姓名必须来自用户资料，禁止再用关系字段冒充姓名。
- **权限语义**：长辈决定家属能否查看健康、代录健康、管理用药、接收紧急通知；家属不能自行给自己提权。双方均可解除绑定。

## 2. 调研依据

本设计先对照项目现有 `docs/designs/ui/` 视觉稿，再参考以下外部资料：

- W3C WAI《Older Users and Web Accessibility》：老年用户常同时受到视力、灵活性、听力和认知变化影响，界面需保持清晰层级、稳定位置和可理解反馈。
  <https://www.w3.org/WAI/older-users/>
- WCAG 2.2 目标尺寸说明：交互目标最低边界为 24 × 24 CSS px；本项目继续执行既有移动端审计的 44px 可见触控下限，高频长辈操作优先 48–56px。
  <https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html>
- WCAG 2.2 一致帮助说明：帮助与支持入口应保持位置一致；本项目将通知、语音、设置继续放在稳定的页头和底栏位置。
  <https://www.w3.org/WAI/WCAG22/Understanding/consistent-help.html>
- PubMed 2026《An mHealth Design Framework for Older Adults》（PMID 42175272）：将老年用户需求纳入移动健康产品的用户中心设计；本项目据此区分长辈端“大而直接”和监护端“紧凑但不牺牲触控”的密度策略。
  <https://pubmed.ncbi.nlm.nih.gov/42175272/>

调研不改变项目既有品牌与双主题，只用于校准密度、触控、信息层级和图表选择。

## 3. 页面信息架构

### 3.1 家属看板 `/`

首屏按以下顺序组织：

1. 页头：家人看板、v1.1 通知铃铛；
2. 长辈选择 Tab：头像/姓名/关系，最后一个为添加长辈；
3. 关键统计：
   - 今日用药完成数与完成率；
   - 7 日用药完成率迷你柱图；
   - 最近生命体征与 7 日趋势 SVG；
   - 7 日异常记录次数；
4. 快捷操作：记录健康、设置用药；
5. 最近提醒或碎碎念消息。

图表只使用轻量内联 SVG，不引入图表运行时。图形必须同时提供文字结论，颜色不是唯一信息载体。

### 3.2 健康 `/health`

- 长辈端：展示本人数据，可新增本人记录。
- 家属端：顶部固定显示当前长辈选择器，卡片标题使用“父亲的健康”等明确主体；新增记录时服务端强制 `recorded_by=当前家属`、`input_method=family`。
- 卡片以当前看板卡片为基准：36–40px 语义化 SVG 图标、最新值、状态、更新时间、迷你趋势；去掉纯装饰的大面积空白。
- 家属没有“监护人自己的健康数据”入口，避免主体混淆。

### 3.3 用药 `/medicine`

- 双角色都可为目标长辈创建和编辑用药计划；家属端必须先选择长辈并通过 `can_edit_medication`。
- 正式挂载现有计划表单，补提醒开关、提前分钟数和计划创建者说明。
- 今日发生项必须有完整 `scheduled_at`，显示仍使用本地 `HH:mm`；确认服药以 `(plan_id, scheduled_at)` 幂等写入。
- 只在到达提醒窗口且 `remind_enabled=true` 时朗读提醒，不能进入页面就朗读第一条未服计划。

### 3.4 消息与通知

- `/notifications` 展示 v1.1.0 更新通知，并由首页铃铛与设置页进入。
- `/messages` 联系人由一个聚合接口返回姓名、关系、最后消息和未读数，替代每位联系人两次请求。
- AI 整理并经长辈确认同步的内容以普通文字消息落库，同时带独立 `category=murmur`；聊天气泡和联系人预览显示“碎碎念”标签，不把业务标签塞进 `type=text|voice`。
- 对话页背景使用统一页面底色与气泡层级，不给底栏当前项增加局部圆形底色。

### 3.5 设置与关于

- 设置页顶部资料卡缩小高度，增加与页面语义一致的 SVG 图标和清晰分组。
- “消息通知”与“关于我们”从占位改为可进入页面。
- 关于我们固定文案：华中科技大学基础医学院“慧老智治医心为民”AI智慧医养暑期实践项目。
- 版本展示统一为 v1.1.0。

## 4. 组件规范

### 4.1 按钮

| 级别 | 高度 | 用途 |
|---|---:|---|
| `sm` | 44px | 次级紧凑操作 |
| `md` | 48px | 项目默认按钮，等同看板 Tab 的触控密度 |
| `lg` | 52px | 页面主操作 |
| 特殊大按钮 | 56px 以上 | SOS、确认服药、纯圆形语音按钮，保持独立规格 |

按钮默认圆角收敛到中等圆角；纯圆形按钮不变。禁止普通按钮再以 56px 以上高度和过大上下 padding 占据整行。

### 4.2 开关

- 可点击盒 48 × 48px；可见轨道约 44 × 26px；
- 开启使用当前主题操作色，关闭使用中性底色；
- 统一使用共享 `Switch` 组件，保留 `role=switch`、`aria-checked` 和禁用状态。

### 4.3 底部导航

- 五项继续共享 64px 网格和安全区；
- 未选中图标为镂空，选中图标使用 `fill=currentColor`；
- 选中状态只改变图标/文字颜色和字重，不再显示局部圆形或整项色块高亮；
- 纯圆形语音主按钮不属于底栏当前项高亮规则。

### 4.4 卡片

- 默认内边距 16px，摘要卡可为 12px；
- 圆角、边框和阴影沿用当前主题变量；
- 用 36–40px 语义图标容器、右下低透明 SVG 印记、状态 Badge 和紧凑数据行建立层级；
- 设置首页、健康、用药、通知页面统一套用，不做互不相干的新风格。

## 5. 服务端与 Supabase 契约

Next Route Handler 仍是唯一业务权限边界；服务端 secret key 绕过 RLS，因此每个跨用户请求必须先做绑定与权限校验。

### 5.1 绑定

- `GET /api/v1/family/binds` 返回绑定字段与最小 `peer`：`id/name/avatar_url/last_active_at`；
- `generate-code` 只允许 elder；`bind` 只允许 family；
- 绑定码使用加密安全随机数、有效期和唯一约束，兑码使用条件更新防并发重复消费；
- PATCH 先校验归属；只有 elder 可更新授权位；DELETE 双方均可执行；
- 新增 `can_edit_health`，默认允许，长辈可关闭。

### 5.2 健康

- 所有 GET 接受显式 `user_id`；Store 按目标 ID 隔离请求并防止快速切换串数据；
- 家属 POST 仅在 active 绑定且 `can_edit_health=true` 时允许；服务端覆盖 `recorded_by` 与 `input_method`；
- latest 由五次串行查询改为一次查询后按类型归并。

### 5.3 用药

- 所有 GET/POST 接受显式目标长辈；`created_by`、服药确认人由服务端填写；
- 今日时间按 `Asia/Shanghai` 组合为完整 `scheduled_at`；
- 服药记录以 `(plan_id, scheduled_time)` 唯一并 upsert；查询按 `scheduled_time` 的日范围，不再按 `created_at`；
- 创建记录前校验 plan 属于目标长辈。

### 5.4 碎碎念与消息

- 消息增加独立 `category`（`chat|murmur|system`）；
- 新增照护笔记表保存语音对话整理结果，即使用户不分享也可留存本人笔记；
- 分享动作只允许选择当前长辈的 active 家属，消息强制 `is_ai_generated=true`、`category=murmur`。

### 5.5 MiMo 工具调用

`POST /api/v1/ai/chat` 改用服务端 `mimo-v2.5-pro`，系统提示词定义“小护”为陪伴型老年助手，并声明工具：

1. `record_health_data`：从明确陈述中提取并记录体征；
2. `save_care_note`：整理碎碎念并保存；
3. `share_care_note`：只有获得老人明确同意后，整理为适合家属阅读的文字并发送给 active 家属。

服务端执行工具、记录 action 结果，再把工具结果回传模型生成最终自然语言回复。模型不得诊断、开药或在没有明确同意时向家属发送隐私内容。语音页继续展示文字并通过 MiMo TTS 朗读最终回复。

## 6. 性能预算

- 家属看板使用单个聚合接口，避免 latest/today/trend 三次往返和全局 Store 串写；
- 联系人摘要使用一次服务端聚合，避免 2N 请求；
- 未读消息改为批量已读；
- 健康 latest 合并为一次 Supabase 查询；
- 统计图使用内联 SVG，不新增图表依赖；
- 非首屏页面继续按路由拆包，避免在首页预载表单与语音实现；
- 保持现有构建预算：CSS 单文件 ≤100 KiB、CSS 总量 ≤200 KiB、JS 单文件 ≤250 KiB、JS 总量 ≤1,100 KiB。

## 7. 数据迁移策略

迁移只做向后兼容的新增与约束补强，不删除历史数据：

1. 新增绑定权限、绑定码过期时间；
2. 新增消息 category、照护笔记表、服药确认人；
3. 新增幂等唯一索引和必要查询索引；
4. 旧关系值不做不可靠的自动父/母推断；UI 对旧值显示“待确认关系”，由用户重新选择；
5. 先提交并验证本地 migration，再通过 Supabase MCP 应用并生成最新 TypeScript 类型。

共享 Supabase 中其他项目存在未启用 RLS 的表，本次仅修改 `oc_*` 范围，不擅自处理其他项目表。

## 8. 验收标准

- 家属选择不同长辈时，健康、趋势、用药、统计和新建记录都严格对应当前长辈；
- 家属不能访问未绑定长辈，也不能自行开启授权；
- 性别/出生日期可保存、清空，并得到明确校验错误；
- 确认服药真实落库，刷新后仍显示已服；
- 双角色均能创建用药计划，提醒只在正确窗口触发；
- MiMo 对话能够真实记录健康、保存碎碎念，并在明确同意后向对应家属发送带“碎碎念”标签的消息；
- 通知页与关于页可达，版本统一为 v1.1.0；
- 页面无横向溢出，可见交互目标不小于 44px，底栏选中态无局部高亮色块；
- `npm test`、`npm run lint`、`npm run tsc`、`npm run build` 全部通过；
- `next.config.ts` 不含 `output: 'export'`，无 `.env*` 或真实密钥进入提交。
